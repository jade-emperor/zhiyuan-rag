# 面试八股 · 部署与工程化

> 自写的演示语料：题目与答案是通用技术知识，不是任何机构的材料。

### 32. 怎么估算一个大模型要多少显存

按四块算：**权重**、**KV 缓存**、**激活与临时张量**、**框架开销**。
权重最简单：参数量 × 每参数字节数（FP16 是 2，INT8 是 1，INT4 是 0.5）——
7B 的 FP16 就是 14 GB。KV 缓存按 `2 × 层数 × 头数 × 头维度 × 序列长度 × batch × 字节数` 估，
长上下文下它会超过权重。激活值与 batch、序列长度成正比，训练时还要加上优化器状态
（Adam 的动量与方差各一份，全参训练约等于权重的 4～6 倍）。

所以"能不能跑"要连着问三件事：什么精度、多长上下文、多大并发。
经验做法是先按权重 + 预留 20% 估算，再用真实流量压一遍看峰值。

### 33. 推理服务的首 token 延迟和吞吐怎么权衡

首 token 延迟（TTFT）由**预填充**决定：要把整段提示词过一遍前向，提示越长越慢；
吞吐由**解码**决定：一次生成一个 token，能否批处理是关键。
两者互相拉扯 —— 把 batch 开大吞吐上去了，但排队让 TTFT 变差；
把提示截短 TTFT 好了，答案质量可能下降。

常见手段：**连续批处理**（continuous batching，请求跑完就出队、新请求立刻补位）、
**前缀缓存**（多轮对话里复用系统提示与历史的 KV）、**分页注意力**（PagedAttention 管理 KV 显存碎片）。
线上要分开定 SLO：交互式场景保 TTFT（<1s），离线批任务保吞吐（tokens/s per GPU）。

### 34. 限流该怎么做，为什么选滑动窗口

先分清三种算法：**固定窗口**实现最简单，但窗口边界会放过 2 倍流量（前一窗口末尾 + 后一窗口开头）；
**漏桶/令牌桶**能平滑流量、允许突发，但要额外维护令牌状态；
**滑动窗口**用时间戳队列或分段计数，任何时刻都只看"最近 N 秒"，边界问题自然消失。

工程上滑动窗口常落成 **Redis ZSET + Lua**：Lua 里原子完成"裁剪过期成员 → 计数 → 判定 → 写入 → 设 TTL"，
避免"读-改-写"之间的竞态；用服务端时间而不是客户端时间，防改表绕过。
限流**失败时要降级**（放行 + 打日志 + 标记 degraded），而不是让整个问答挂掉 ——
限流是保护措施，不该成为新的单点。

### 35. 缓存能省什么，怎么避免脏数据

三类缓存价值最高：**嵌入结果**（同一段文本反复嵌入是纯浪费）、
**检索结果**（热点问题的召回集合短时间内不变）、**生成结果**（FAQ 类问题答案唯一）。

脏数据的根因是"数据变了、缓存没变"。做法有两层：
① **按内容指纹做键**（语料变了指纹就变，旧键自然失效），比按时间失效更准；
② 给缓存设**短 TTL**（秒级到分钟级）作为兜底，并让写入路径**显式失效**相关键。
要特别小心"缓存了错误结果"：报错、拒答、空结果**一律不缓存**，
否则一次故障会被缓存放大成持续故障。命中率是手段不是目标 —— 先保证正确性，再谈命中率。

### 36. 上线一个新版本怎么做灰度与回滚

先把"回滚"设计好再上线：**产物可寻址**（镜像 tag 固定、不覆盖），
**配置与代码分离**（回滚代码不用改配置），**数据层兼容**（新代码写的数据，旧代码要能读，
或者双写过渡）。灰度按流量比例或按用户分桶，每档都要看**业务指标**（拒答率、满意度）
而不是只看 CPU 和 QPS —— 服务健康但答得更差，是最常见的灰度事故。

判据要提前定：错误率、p95 延迟、拒答率超过阈值就自动回滚；
回滚动作本身要演练过（很多人第一次用回滚脚本就是在故障里）。
另外**别在同一时刻同时改模型、提示词和检索参数** —— 出了问题无法归因。

### 37. 为什么日志里要有 request_id，账本要记什么

没有 request_id 时，一次"答得不对"的排查要从几万行日志里靠时间戳猜，
而且并发一上来根本无法确定哪几行属于同一个请求。所以入口生成 request_id、
贯穿检索/嵌入/生成各段，并在响应头与答案里带出去 —— 用户报问题时能直接给你 ID。

延迟账本要按请求一行：**渠道**（FAQ 直答 / 知识库 / 寒暄 / 限流兜底）、**冷热**
（是不是冷启动那几次）、**分段耗时**（检索、重排、生成、首 token）、
以及**拒答/截断/中断**三个布尔量。有了这些才能回答"变慢了是哪一段变慢"、
"质量掉了是因为拒答变多还是检索变差"—— 只有平均响应时间的话，什么都定位不了。
