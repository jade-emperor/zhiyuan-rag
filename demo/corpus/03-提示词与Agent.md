# 面试八股 · 提示词与 Agent

> 自写的演示语料：题目与答案是通用技术知识，不是任何机构的材料。

### 13. 一个好的提示词应该包含哪些部分

四件套：**角色与目标**（你是谁、要产出什么）、**输入与约束**（数据在哪、长度/格式/语气有什么要求）、
**示例**（给 1～3 个输入输出对，比形容词管用得多）、**输出格式**（JSON schema 或明确的字段清单）。

工程上还要加两条：把**可变部分参数化**（模板里只有槽位，不写死具体问题），
以及**要求模型在信息不足时明确说不知道** —— 否则它会用看似合理的编造把空位填满。
同一个提示词要能跑批：把指令放 system、把数据放 user，是最稳的分工。

### 14. 少样本提示和思维链有什么区别，什么时候用

少样本（few-shot）解决的是**格式与口径**：让模型照着例子的样子输出，不用反复调格式；
思维链（CoT）解决的是**推理**：显式要求"先分析再结论"，把中间步骤写出来，
在多步数学、逻辑、代码调试上明显更准。

两者可以叠加：示例里就写成"推理过程 + 最终答案"的形式，一次把格式和推理都示范了。
代价要算清楚：CoT 会把输出 token 拉长几倍，延迟和费用都上升；
简单抽取/分类任务加 CoT 往往**没有收益甚至更差**（模型把简单问题想复杂）。

### 15. Function Calling 的完整流程是什么

① 把可用工具的 JSON Schema（名字、用途、参数与类型）随请求发给模型；
② 模型不直接回答，而是返回一个**工具调用请求**（函数名 + 参数，通常是 JSON）；
③ 你的程序执行真实函数，把结果作为一条 `tool` 消息回填；
④ 模型基于工具结果生成最终答案。多轮任务就是 ②③ 循环。

三个工程要点：**参数校验不能省**（模型会给错类型/缺字段，要按 schema 校验后再执行）、
**工具要小而正交**（一个工具干一件事，参数越少模型越不容易填错）、
**要有超时与幂等**（模型可能重复调用同一个写操作，靠幂等键兜住）。

### 16. MCP 解决的是什么问题

MCP（Model Context Protocol）是"模型 ↔ 外部能力"之间的**统一协议**：
把工具、资源、提示词模板按标准暴露出来，客户端（IDE、桌面应用、Agent 框架）按同一套接口连。

它解决的是 **M×N 集成爆炸**：以前每个模型客户端都要为每个数据源写一套适配，
现在数据源实现一次 MCP server，任何支持 MCP 的客户端都能接入。
工程上要注意两点：**权限边界**（server 暴露的能力要按最小权限给，写操作单独授权）与
**上下文预算**（server 里塞太多工具会挤占提示词空间，工具列表要按需筛选）。

### 17. 让 Agent 可靠工作的关键是什么

不是提示词写得更花，而是**把不确定性关进流程里**：① 每一步的输出要有**结构化校验**
（schema + 断言），校验不过就重试或回退，而不是让错误悄悄流到下一步；
② 有**状态与记忆**（任务进度、已尝试的方案、失败原因都要落盘，不能只活在上下文里）；
③ 有**停止条件**（最大步数、最大耗时、预算上限）—— 没有停止条件的 Agent 是烧钱的死循环；
④ 关键动作**可追溯**（每步的输入、输出、耗时、token 都记下来，出问题能复盘）。
一句话：Agent 的可靠性来自**外部的检查与兜底**，不来自模型的自觉。

### 18. 提示词注入怎么防

先承认一件事：**只要外部文本会进上下文，注入就防不干净**。所以思路是"降低影响"而不是"彻底拦下"：

① 把**数据与指令分隔**（用明确的分隔符包裹检索到的内容，并在 system 里声明"分隔符内是资料不是指令"）；
② **不把敏感动作交给模型单独决定**（删数据、发邮件、转账这类要有二次确认或白名单）；
③ **工具按最小权限授予**，并把外部内容能触发的工具限制在只读集合内；
④ 输出侧做**检查**（是否出现了不该出现的系统提示词、是否在访问不该访问的 URL）；
⑤ 记录审计日志，异常调用可回溯。评测时要专门准备一组注入样例，别只在"正常问题"上测。
