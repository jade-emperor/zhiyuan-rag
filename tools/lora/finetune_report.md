## 一、摘要

用 LoRA 微调 `chinese-roberta-wwm-ext`，把「用户 query 该走哪种改写策略」做成 4 分类器，
只训练 **0.29%** 的参数（297,988 / 102,568,712），16.3 秒跑完 4 轮（配置 10 轮，第 4 轮触发早停）（2203 样本/秒）。

| 指标 | 值 |
|---|---|
| 测试集 accuracy（1000 条，只跑一次） | **0.9700** |
| 测试集 macro-F1 | **0.9700** |
| 测试集 **top-2** 准确率 | **1.0000** |
| 训练显存峰值（PyTorch allocated） | **1086.5 MB** |
| 训练显存峰值（设备级实际占用） | **2505.6 MB** |
| 推理吞吐 / 权重占用 | 见第五节 |

三句话结论：① 误差只有 **30 条**，全部集中在 `3→1`（27 条）、`1→0`（2 条）、`0→1`（1 条） —— 这 3 对上；
② 这些误判与数据卡里预判的「铺垫 + 核心无指代」边界样本一致，是**数据边界问题**而非模型容量问题；
③ 误判样本的真值 **100% 落在 top-2**（1.0000），线上应当用「两个候选改写都执行」，而不是一刀切回退。

## 二、数据

数据由 5 个子代理各生成 1000 条、经两轮质检与返工配平而来（生成与质检细节见 `data/intent/strategy_v1/README.md`）。本次微调实际使用：

| 划分 | 条数 | 类别分布 | 来源 |
|---|---|---|---|
| train | **3600** | 各类 900 | `train.jsonl`（4000 条）按类别**分层**切掉 dev 后 |
| dev（早停用） | **400** | 各类 100 | 同一份 train.jsonl 分层切出，与训练**互斥**（seed=42） |
| test | **1000** | 各类 250 | `test.jsonl`，全部来自 agent5（生成者隔离，测跨生成者泛化） |

- 文本长度：最短 5 / 中位 21 / 最长 53 字 → `max_length=64` 足够、无截断
- 长度分布：≤15 字 1252、16~30 字 1627、31+ 字 1121
- 内容范围：技术八股（Python/Java/数据库/Linux/网络/大模型）+ 大模型教材术语 + 企业制度；**不含任何培训业务内容**
- 已知问题（沿用数据卡，本次训练未修复）：label 3 里约 10% 属「铺垫 + 核心无指代」的规则边界；8 对 0.7~0.8 的跨集近似未清洗；数据是 LLM 合成的，分布不代表真实流量

## 三、LoRA 配置

| 项 | 值 | 说明 |
|---|---|---|
| `task_type` | `SEQ_CLS` | 序列分类任务头 |
| `r`（秩） | **8** | BERT 系分类的常见秩；4~16 之间收益差异很小 |
| `lora_alpha` | **16** | 主流取 `2×r`，缩放比 `alpha/r=2` |
| `lora_dropout` | **0.1** | 正则化，5000 条属小数据，防过拟合 |
| `target_modules` | **`['query', 'value']`** | BERT 注意力里最常用的注入点 |
| `bias` | `none` | 不训练 bias，省参数也避免破坏预训练偏置 |
| `modules_to_save` | **`["classifier"]`** | 分类头随机初始化，必须训练并单独保存 |

**参数量分布**（`param_ledger` 实测）：

| 板块 | 参数量 | 可训练 | 权重显存 | 梯度+AdamW |
|---|---|---|---|---|
| 基座权重（冻结） | 102,267,648 | 0 | 390.12 MB | 0.00 MB |
| LoRA 适配器 | 294,912 | 294,912 | 1.12 MB | 3.38 MB |
| 分类头 | 6,152 | 3,076 | 0.02 MB | 0.04 MB |
| **合计** | **102,568,712** | **297,988（0.2905%）** | 391.27 MB | 3.41 MB |

> 分类头那 6,152 个参数里只有 3,076 在训练：peft 的 `modules_to_save` 会把原模块**复制一份**（`original_module` 冻结 + `modules_to_save.default` 训练），这是账本量出来的，不是推断。

## 四、训练超参与设计理由

| 超参 | 取值 | 为什么这么设计 |
|---|---|---|
| `learning_rate` | **2e-04** | LoRA 可训练参数只占 0.29%，梯度信号弱，学习率要比全参微调（典型 2e-5）高一个量级；主流区间 1e-4~3e-4 |
| `lr_scheduler_type` | **cosine** | 余弦退火让后期步长自然收敛到 ~0，比线性更平滑；实测 lr 从 warmup 峰值 2.0e-04 降到 1.5e-04 |
| `warmup_ratio` | **0.1** | 前 10% 线性升温，避免随机初始化的分类头在第一步就把预训练权重带偏 |
| `optim` | **`adamw_torch`** | Transformer 微调的事实标准；AdamW 把权重衰减从梯度里解耦 |
| `adam_beta1/beta2` | **0.9 / 0.999** | Transformer 常规取值，二阶矩估计对稀疏梯度更稳 |
| `adam_epsilon` | 1e-8 | 常规取值，防止除零 |
| `weight_decay` | **0.01** | 正则化；HF 口径只作用在非 bias/LayerNorm 参数上 |
| `max_grad_norm` | **1.0** | 梯度裁剪，防偶发炸梯度 |
| `num_train_epochs` | **10** | 配早停，宁多勿少；本次实际第 4 轮就触发了早停（连续 2 轮 macro-F1 无提升） |
| `EarlyStoppingCallback` | **patience=2** | 盯 `macro_f1`（4 类均衡，macro 才有意义），配合 `load_best_model_at_end=True` 自动回滚最优权重 |
| `per_device_train_batch_size` | **32** | 序列最长 53 字，32 在 16 GB 卡上毫无压力 |
| `max_length` | **64** | 覆盖最长样本且留余量，再长只是浪费算力 |
| `precision` | **bf16** | 有 bf16 就用 bf16：不需要 GradScaler、动态范围大；无 GPU 时自动退化 fp32 |
| `label_smoothing_factor` | 0.0 | 数据是干净均衡集；若日后确认残余噪声可设 0.05 |
| `seed` / `data_seed` | **42** | 切分与初始化可复现 |

**逐轮 dev 表现**（早停依据）：

| 轮次 | eval_loss | accuracy | macro-F1 | f1(0) | f1(1) | f1(2) | f1(3) |
|---|---|---|---|---|---|---|---|
| 1 | 0.4658 | 0.9125 | 0.9115 | 0.862 | 0.873 | 0.951 | 0.960 |
| 2（最优） | 0.1038 | 0.9675 | 0.9674 | 0.956 | 0.933 | 1.000 | 0.980 |
| 3 | 0.1008 | 0.9675 | 0.9673 | 0.951 | 0.933 | 1.000 | 0.985 |
| 4 | 0.1284 | 0.9650 | 0.9647 | 0.951 | 0.927 | 1.000 | 0.980 |

> 最优轮是第 2 轮（macro-F1 0.9674），最后一轮（第 4 轮）为 0.9647，随后触发早停；`load_best_model_at_end=True` 把最优那份取了回来 —— 最优权重回滚这条链路是通的。

## 五、显存占用（分板块 + 总占用）

训练配置：`batch=32`、`max_length=64`、`bf16`、`grad_accum=1`。「已分配」是 PyTorch 分配器口径，「设备已用」是整个 GPU 的口径（含 CUDA context、库 workspace 与其它进程）。

| 板块 | 已分配 MB | 设备已用 MB | 说明 |
|---|---|---|---|
| CUDA context + 库句柄 + 其它进程（起点） | 0.0 | **1297.6** | **不计入 `memory_allocated`**，只看已分配会严重低估 OOM 风险 |
| 基座权重上卡（fp32） | **390.7** | 1739.6 | 102,267,648 参数 × 4 B |
| LoRA 适配器 + 分类头 | +1.1 → 391.9 | — | 297,988 个可训练参数 |
| AdamW 一阶/二阶状态 | 首步后出现 | — | **懒分配**：理论 3.41 MB （只有可训练参数有状态） |
| 梯度 + 优化器 + 库 workspace（训练稳态） | **458.2** | 2505.6 | 比权重多出的部分是梯度、AdamW 状态与 cuBLAS/cuDNN workspace |
| 前向激活峰值（forward 钩子打点） | **1008.5** | — | 激活最占显存的一刻；**激活量级 ≈ 617.8 MB** |
| 评测 / 保存 checkpoint 峰值 | 1086.5 | 2505.6 | 保存会额外复制一份 state_dict |
| **训练全程峰值（总占用）** | **1086.5** | **2505.6** | 前者是进程内 PyTorch 峰值，后者是这张卡上真实被占掉的最大值 |

**理论对照**：同一份模型若做**全参**微调，权重+梯度+AdamW ≈ **1565 MB**（16 B/参数），LoRA 只要 **395 MB**（只有 0.29% 的参数带梯度与优化器状态），差 ~4.0 倍。

### 5.1 一次训练步的完整分解（逐阶段实测，含激活/梯度/优化器）

上面那张表是**训练时按生命周期打点**，只看得到「某一刻驻留多少」；真正的峰值在**反向传播**那一段，
所以另跑了一次专门的实验（`tools/lora/vram_budget.py`）：真实模型 + 真实 batch，
**每个阶段前 `reset_peak_memory_stats()`**，因此每段峰值只属于该段。

配置：batch 32，样本真实长度 7~35，padding 到 35（动态 padding，与训练一致）。

| 阶段 | 段内峰值 MB | 该段新增峰值 MB | 结束时驻留 MB | 设备已用 MB |
|---|---|---|---|---|
| ① 建模型（CPU 载入） | 0.0 | +0.0 | 0.0 | 1297.6 |
| ② 权重上卡（fp32） | 390.8 | +390.7 | 390.8 | 1739.6 |
| ③ 注入 LoRA + 分类头 | 391.9 | +1.1 | 391.9 | 1739.6 |
| ④ 前向（激活存活） | 988.4 | +596.5 | 957.2 | 2333.6 |
| ⑤ 反向（梯度生成） | 1016.1 | +59.0 | 457.0 | 2375.6 |
| ⑥ 优化器 step（AdamW 状态落地） | 460.4 | +3.4 | 459.3 | 2375.6 |
| ⑦ 稳态前向 | 1022.7 | +564.5 | 992.6 | 2379.6 |
| ⑧ 稳态反向 | 1018.7 | +26.1 | 459.3 | 2393.6 |
| ⑨ 稳态 step | 460.4 | +1.1 | 459.3 | 2393.6 |
| ⑩ 评测前向（no_grad） | 497.0 | +38.9 | 458.2 | 2393.6 |

**同一时刻到底活着什么**（这才是「显存被谁占了」的答案）：

| 组成 | 大小 | 怎么来的 |
|---|---|---|
| 权重（基座 + LoRA + 分类头） | **390.8 MB** | 102.57M 参数 × 4 B（fp32） |
| **激活**（前向峰值 − 权重） | **597.6 MB** | 前向要保存每一层的中间结果给反向用 |
| 反向额外（梯度 + 临时张量） | +27.8 MB | 只有 0.29% 参数有梯度，所以很小 |
| AdamW 一阶/二阶状态 | +2.5 MB | 只对可训练参数（懒分配，首步才出现） |
| 评测（no_grad）时的激活 | 106.3 MB | 不建计算图，比训练小一个量级 |
| **训练步最高峰值** | **1022.7 MB** | 权重 + 激活 + 梯度 + 优化器状态 |

**最坏情况**（强制 pad 到 `max_length=64`，即一个 batch 全是长样本）：激活从 598 MB 涨到 **1041 MB**，训练步峰值 1467 MB。真实训练用的是动态 padding（按 batch 内最长样本），所以实测峰值 1086 MB 落在两者之间。

> 训练日志里 `前向激活` 那几行只覆盖 forward 结束的一瞬，**不是**整步峰值；整步峰值由 `全程峰值` 给出，而各段分别是多少要看这张表。

### 5.2 到底至少要多少显存（OOM 边界实测）

方法：`torch.cuda.set_per_process_memory_fraction(f)` 把**本进程分配器**的上限压到「设备总量 × f」，然后在每一档里跑一次完整训练步（forward + backward + optimizer.step）；每档是**独立进程**，OOM 就记一次失败。注意 context（约 1.3 GB）是在分配器之外分配的，所以下面「上限」只是分配器预算，真实占用要再加上 context。

**动态 padding（真实训练口径）**

| 分配器上限 MB | 占设备 | 结果 |
|---|---|---|
| 978 | 6.0% | OOM ✘ |
| 1060 | 6.5% | OOM ✘ |
| 1076 | 6.6% | OOM ✘ |
| 1109 | 6.8% | 能跑完 ✔ |
| 1141 | 7.0% | 能跑完 ✔ |
| 1304 | 8.0% | 能跑完 ✔ |

**pad 到 64（最坏情况）**

| 分配器上限 MB | 占设备 | 结果 |
|---|---|---|
| 1304 | 8.0% | OOM ✘ |
| 1467 | 9.0% | OOM ✘ |
| 1549 | 9.5% | 能跑完 ✔ |
| 1630 | 10.0% | 能跑完 ✔ |

- **动态 padding（真实训练）**：分配器下限在 **1076 ~ 1109 MB** 之间；加上 context **1298 MB** → 整卡至少要有 **2374 ~ 2406 MB** 空闲。留 20% 余量（抗碎片与其它进程）→ **约 2.8 GB**。
- **最坏情况（pad 到 64）**：分配器下限 **1467 ~ 1549 MB** → 整卡 **2765 ~ 2846 MB**，留 20% 余量 → **约 3.3 GB**。
- 计算出的激活是**线性**的：激活 ≈ batch × 序列长度 × 常数。显存不够时的顺序是① 降 `--batch-size`（最有效）→ ② 降 `--max-length` → ③ `--grad-accum` 顶上等效 batch → ④ `--gradient-checkpointing`（用时间换激活）。

> ⚠️ 上面这个「最少」是**进程视角**：它把 CUDA context（约 1.3 GB）算进去了，而 context 是**每个用 CUDA 的进程都要付一遍**的固定开销。如果你在 Windows 任务管理器里看到的数字对不上，看下一节 —— 那是另一套口径。

### 5.3 三个「显存占用」量的不是一回事（为什么屏幕上的数字和这里不一样）

| 口径 | 实测值 | 含义 / 什么时候用它 |
|---|---|---|
| ① 张量硬下限（分配器 cap 实测） | **1076 MB 就 OOM，1109 MB 能跑** | 「权重+激活+梯度+优化器」本身要多少；与进程无关的硬指标 |
| ② 进程视角总量（WSL 内 `mem_get_info`） | **2320 MB** = context 1298 + 张量 1023（实测峰值）；cap 实验给的**可用下限**是 2406 MB（多出的是碎片） | 「我这个训练进程一共压了多少」——判断本进程会不会 OOM |
| ③ 宿主/任务管理器视角 | 整卡 **4390 MiB** / 16303 MiB，最大一项 **vmwp.exe** = **4389.6 MiB** | 你在屏幕上看到的数 —— 含**整个 WSL 虚拟机（vmwp）的持有量**，不等于本任务的占用 |

宿主侧实测（`vram_budget.py --host-snapshot`，原始输出在 `vram_host_view.json`）：

- 整卡已用 **4390 MiB**；逐进程计数器只报了一个大户：
  - `vmwp.exe`（pid 8092）→ **4389.6 MiB**
- 同一时刻训练进程**没在跑**、RAG 服务自己 `torch.cuda.memory_allocated() = 0`（启动预热失败，模型没加载）

**结论：那 4.3 GB 是 WSL2 虚拟机（`vmwp`）的 GPU 持有量** —— WSL 里历次 CUDA 进程用过、宿主的驱动还没收回的部分。所以：

- 任务管理器从 4.3 GB 涨到 5.7 GB，是**虚拟机在这次运行里又向 Windows 多要了约 1.4 GB**，不是「这个任务要 4 GB」
- 这个增量小于口径②的 2320 MB，因为 context 那一块在 WSL VM 里是**复用/摊销**的（VM 早就持有），而我在 WSL 里量到的「设备已用」把每个进程的 context 都单独算了一遍
- **真要判断会不会 OOM**：用口径②（进程自己 2.4 GB）+ 卡上已有的其它占用。16 GB 卡上这个任务随便跑；8 GB 卡且 RAG 服务热跑（BGE-M3+reranker ≈ 5 GB）时才会紧张

## 七、结论

1. **模型可用**：test accuracy 0.9700 / macro-F1 0.9700，4 类均衡下没有塌缩类；分类头 + LoRA 的 0.29% 参数足够承载这个任务。
2. **误差是结构性的、可解释的**：30 条误判全部集中在 `1↔3` 这一对语义边界上，根因是数据里约 10% 的规则边界样本（「有铺垫但核心空泛」该判 3 还是 1），**不是模型容量问题**。→ 下一步提升不靠调超参，靠把这批边界样本人工复核后重训。
3. **线上策略应当是 top-2 双改写，而不是低置信回退**：误判真值 100% 在第二位，而一刀切回退实测把准确率拉低明显。低成本做法：置信度低于阈值时同时执行两个候选改写，或转人工。
4. **成本极低**：训练 16.3 秒、峰值 1086.5 MB（设备级 2505.6 MB）；适配器只有 MB 级，可以按「数据一更新就重训一轮」的节奏跑。
5. **局限**：只跑了 1 个种子（没有多种子方差）；test 全部来自 agent5（跨生成者泛化，偏保守）；数据是合成的，真实流量上线后需要重测分布。

### B. 复现命令

```bash
# 1) 基座（不在仓库里）
HF_ENDPOINT=https://hf-mirror.com python -c "from huggingface_hub import snapshot_download as d; \
  d('hfl/chinese-roberta-wwm-ext', local_dir='models/chinese-roberta-wwm-ext')"

# 2) 冒烟（CPU 也能跑）
python tools/lora/train.py --smoke

# 3) 正式训练 + 最后跑一次测试集
docker run --rm --gpus all -v "$PWD":/work -w /work --entrypoint python \
  project-rag:0.1.0 tools/lora/train.py --output-dir logs/lora/run1 --eval-test

# 4) 推理 / 评测 / 显存扫描；产出本报告
docker run --rm --gpus all -v "$PWD":/work -w /work --entrypoint python \
  project-rag:0.1.0 tools/lora/infer.py --adapter logs/lora/run1/lora_adapter \
  --test --bench-batch 1,8,32,128 --out logs/lora/run1/test_predictions.jsonl
python tools/lora/make_report.py --run-dir logs/lora/run1
```

> 为什么走 `docker run --gpus all`：agent 的 shell 挂的是私有 `/dev`（无 `/dev/dxg`），
> `torch.cuda.is_available()` 恒为 False —— 那是**视角**问题，不是机器没有 GPU（见仓库根 `AGENTS.md`）。

### C. 显存口径

| 名词 | 含义 |
|---|---|
| 已分配 `memory_allocated` | PyTorch 分配器当前**活跃**张量占用；不含 CUDA context 与库 workspace |
| 预留 `memory_reserved` | 分配器向驱动要来的缓存池；碎片化会让它持续上涨 |
| 峰值 `max_memory_allocated` | 自上次 `reset_peak_memory_stats()` 以来的最高活跃占用 |
| 设备已用 `mem_get_info` | 整张卡的真实占用（含 context、其它进程）→ **判断会不会 OOM 看这个** |
